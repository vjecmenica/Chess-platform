# Adjudication and online command policy

The [FIDE Laws of Chess](https://handbook.fide.com/chapter/e012023) define mate possibility as mate after *some* legal sequence, even if the defender helps. The same question governs dead positions (5.2.2), resignation (5.1.2), and flag fall (6.9). This decision also applies articles 9.1–9.5 to online draw claims. The rules below are selected for the planned online game; they are not a claim of full FIDE compliance.

## Deciding whether mate is possible

Use three answers for each side: `impossible` with a sound proof, `possible` with a verified legal move sequence ending in its checkmate, and `unresolved`. Replay a positive witness through the full game lifecycle; a sequence that crosses an earlier automatic result is not a valid witness. An engine score, material count alone, or failure to find a mate never proves the other answer. The synchronous game rules have material proofs, a complete search for some closed pawn positions, and a one-move mate witness. They return `unresolved` otherwise.

Resignation is always accepted in an active game. A proven impossibility ends it as a draw under Article 5.1.2; a proven possibility ends it as a win for the opponent. Otherwise the game enters `pending_adjudication` with the resigning side recorded, no result, and no draw offer. The board and history do not change. Moves, claims, offers, draw responses, and further resignations are rejected while pending. This is a frozen game, not a reversible request.

`resolveResignation` and `resolveTimeout` accept only a positive mate line. The domain replays the complete game history and the line, requires every move to be legal, and requires checkmate by the opponent without an earlier automatic result. A ruling accepts at most 256 plies, so positions needing a longer witness remain pending until that limit is revised. The finished snapshot carries the verified line so it can be persisted. A reviewer ID and evidence string alone do not prove impossibility. A future negative-resolution API needs a checkable complete proof or a separately specified, authorized review process that validates and retains the proof before changing the result. Until then, an unresolved no-mate case stays pending. This is an interim limitation, not full FIDE adjudication.

| Approach | Correctness | Cost and fit |
| --- | --- | --- |
| Sound material rules and closed-position search | A negative answer is safe; coverage is incomplete. | Fast and maintainable in the domain; keep as the first pass. |
| Bounded cooperative search | A replayed legal mate line proves `possible`; search exhaustion proves nothing. | Implemented as a separate domain call, ready for a future worker. It never runs on move submission. |
| Exact reachable-state search or a cooperative endgame database | Exhausting every legal successor proves a negative, and a path proves a positive. | Useful for small, closed classes; building, storing, and verifying general coverage is too costly for the initial game server. |
| Chess engine evaluation or Syzygy WDL/DTZ alone | A drawing evaluation or perfect-play result cannot rule out a cooperative mate. | Useful for finding candidate lines, never as a negative certificate. Every proposed line must be replayed legally. |

`findResignationMateWitness(game, budget)` and `findTimeoutMateWitness(game, budget)` run only for their matching pending result. They first try known cooperative lines from the standard start and their exact opening prefixes. These are candidate lines, not assumed results: the game API replays and verifies each one. They then search both sides' legal moves with deterministic ordering and iterative depth limits. The default budget is seven plies and 5,000 visited positions; callers may set at most eight plies and 20,000 positions. Seed-line positions also count against the budget. Every returned line passes the corresponding game verifier, which checks the original history and intervening automatic results. Search does not mutate the game. `depth_exhausted` and `budget_exhausted` both mean **unresolved**, never `impossible`. This is useful for the start position and nearby tactical positions, not a completeness claim.

## Resolving a resignation online

The guest server persists games, clocks, pending flags, and accepted resignations. It has a resignation endpoint and can persist a domain-verified mate witness, but has no adjudication worker. Complete the background resolution flow:

The server already authenticates resignation, orders it with moves and flags, persists the frozen or final state and receipt, and returns the saved response on retry. `resolveResignation` locks the game, re-verifies a supplied mate line through the domain, and saves a single final ruling. The remaining work is:

1. Enqueue one durable job keyed by game ID and frozen version after an unresolved resignation commits. Keep ratings, tournament advancement, and other final-result effects on hold.
2. In a worker outside the live command loop, reconstruct the frozen game and run the bounded search. Submit a found line to the existing service method; a failed or exhausted search must leave the game pending.
3. Record worker attempts and retries so a crash cannot lose a case or generate duplicate final events. A larger budget may find a witness. Before any no-mate draw can resolve a pending case, add a negative-resolution path that validates a complete impossibility proof and retains the proof and reviewer identity. The current domain exposes no such command; a mere evidence string, failed search, or engine evaluation cannot approve a draw.

A pending timeout already stores `flaggedSide` and the effective UTC deadline in PostgreSQL. A future worker will call `findTimeoutMateWitness` and submit a found line to `resolveTimeout`. A verified line changes only the result; it does not play the witness moves or restart either clock. If no line is found, the timeout stays pending. The current server has no queue or worker for this transition.

The server freezes both clocks at flag fall or accepted resignation. The saved history, FEN, turn, and pending reason can be reconstructed after restart; a verified resignation witness is retained with the ruling. For a timeout, the flagged side and effective deadline are saved. Measure how often review is needed before enabling competitive public play. The existing closed-pawn negative proof can still search up to 4,096 states synchronously during adjudication; profile it and move heavy cases off the live command loop before public timed play. A general negative ruling needs a complete proof for that position, such as an exhausted closed graph, not a search timeout.

Standard Syzygy results concern best play and the 50-move rule; they do not answer whether *either* side could help the other reach mate. Cooperative mate reachability is a hard search problem even on generalized boards. See the [Syzygy documentation](https://python-chess.readthedocs.io/en/latest/syzygy.html) and [research on helpmate complexity](https://arxiv.org/abs/2010.09271).

## Incorrect claims online

Treat a claim as one serialized, non-withdrawable command from the player to move. Authenticate the player, check the expected game version, and validate an indicated move's syntax and legality before registering the claim. A malformed or illegal indicated move is rejected as a command: the running clock continues, with no offer or bonus. This is an explicit online adaptation to prevent an invalid payload from pausing the clock. A legal claim whose repetition or move-count threshold is not met is an **incorrect claim**:

1. Stop charging the claimant's clock at the accepted claim's server receipt time while the server decides it. If the threshold is met, finish as a draw without playing the indicated move.
2. If the threshold is not met, add the applicable penalty to the opponent's *remaining* time exactly once. Article 9.5.3 says two minutes; Appendix A.3 changes Article 9 penalties to one minute in rapid, and B.3 applies that rapid rule to online blitz without the specified human arbiter supervision. Determine this from the FIDE time category (base time plus 60 increments), **not** the product's Glicko pool. All 16 currently listed controls fall below 60 minutes by that test, so the planned online setup adds **60 seconds**. If a future control reaches the FIDE classical category, use **120 seconds**. This is an online interpretation of the linked laws; do not label the platform FIDE certified.
3. The incorrect claim is also the claimant's draw offer under 9.1.2.3. It is never an automatic acceptance of an existing offer. Store offers by side so an incoming offer and the new claim offer can coexist. An explicit acceptance identifies which offer is accepted. An accepted move declines only the opponent's offer; an offer ends when declined, accepted, or the game ends.
4. If an intended move was given, execute that **same** validated move in the same serialized operation after the bonus. The claimant cannot change it. Apply the normal legal-move transition and increment once; check mate and automatic results before retaining the claim offer. The move declines an earlier opponent offer. If the claim had no indicated move, leave the board and turn unchanged, publish the claimant's offer, and resume the claimant's clock after adjudication.

Persist the claim receipt, pre-claim state, applicable clock change, any forced move, offers, and resulting version atomically. An identical request retry returns its stored outcome without a second bonus, move, or offer. The current domain returns a rejection with no mutation for an unmet threshold; the clock step must replace that behavior with this complete procedure. Rules for repeated nuisance claims and event-specific draw restrictions need separate moderation policy.

## Ordering with flag falls

The server, not the browser, assigns a player command's receipt time when the complete HTTP body reaches Fastify's `preValidation`, before asynchronous guest lookup. An ingress watermark on every live process holds back a flag while an earlier arrival is being authenticated or admitted. Authorized moves, resignation, and explicit draw actions enter a durable pending-receipt table before competing for the game row. Any server can replay those receipts by `(received_at, admission_id)` after a restart. A flag waits until every live watermark covers the instants before the saved deadline; it drains earlier receipts under the same row lock. A receipt **at or after** the deadline loses to flag fall. Equal-millisecond commands use admission ID as their tie-breaker. Draw claims do not yet use this path. UTC epoch milliseconds survive restart; synchronized host clocks are required for cross-process ordering.

A successful move stops the mover's clock at its receipt. The move, increment, and a clock `handoff` state commit first; neither player is charged while that transaction runs. A second transaction writes the opponent's new start and deadline and completes the durable response. Its timestamp is taken before its brief commit, so that final commit latency is charged to the opponent by explicit policy. If the server crashes between transactions, another worker completes the handoff; no clock runs during the gap. Reject commands received before the new turn's start. A future valid claim will pause time from receipt through adjudication; after an incorrect current-position claim, restart the same turn at the decision's confirmation time. An incorrect intended-move claim commits the forced move and starts the opponent's turn then. A flag result uses the same three-answer mating decision above; `unresolved` freezes the game. For the casual milestone, an already running clock continues through disconnects and outages using its saved UTC deadline.

The transport-free 5+3 clock still implements readiness, monotonic receipt stamping, FIFO processing, and in-memory duplicate IDs for domain use. The guest HTTP path has persisted the new free-first-move start and legacy readiness, deadlines, pending receipts, ingress watermarks, timeout transitions, and restart-safe handoff. A 500 ms poll checks for expiry and pending work; a late callback records the original deadline. A flag changes the saved game to a final no-mate draw, a previously witnessed win, or `pending_adjudication`; it never runs mate-witness search live. Resignation and explicit draw actions now share the receipt ordering, and final or pending resignation stops the clocks at receipt time. A verified resignation witness can be stored through the service, but no worker produces one yet. Claims, their clock effects, and background resolution remain outside the current HTTP flow. An HTTP request lost before durable admission cannot be replayed after its process crashes. A live instance whose database lease expires during a prolonged outage and a host clock that jumps backward need stronger operational handling before public competitive play.
